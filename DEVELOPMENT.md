## Как собрать

```powershell
dotnet build -c Release
```

Требуется .NET 10 SDK. Проект собирается без предупреждений — это не пожелание,
а проверяемое условие: если появится предупреждение, значит что-то сделано неаккуратно.

Запуск:

```powershell
.\src\Cs2LatencyDoctor.Cli\bin\Release\net10.0-windows\cs2latency.exe --seconds 20
.\src\Cs2LatencyDoctor.Gui\bin\Release\net10.0-windows\Cs2LatencyDoctor.Gui.exe
```

Сборка для скачивания (папкой, не одним файлом):

```powershell
dotnet publish src\Cs2LatencyDoctor.Gui\Cs2LatencyDoctor.Gui.csproj `
  -c Release -r win-x64 --self-contained true -o publish\gui
```

**Одним файлом WPF собрать не удаётся.** Режим `PublishSingleFile=true` для этого
проекта падает с ошибкой «Failed to create default extraction directory»: программе
не удаётся создать папку для распаковки встроенных библиотек. Проверено дважды,
поэтому вариант «один exe» в релизах не публикуется.

## Тесты без показа окна

```powershell
tests\Cs2LatencyDoctor.GuiTests\bin\Release\net10.0-windows\guicheck.exe --seconds 5
```

38 проверок: разметка окна, привязки данных, списки, диагностика, история, пауза фона,
слой исправлений и журнал отката, а также правила оценки, которые нельзя проверить
сетью: пороги потерь, определение двухканального режима памяти, фильтр событий
о перегреве, разбор вывода `ping.exe`.

```
ИТОГ: пройдено 38, провалено 0, пропущено 4 (среда запрещает запись в реестр)
```

Третий статус нужен честности ради: если проверку нельзя выполнить в этой среде
(например, запрещена запись в реестр), она помечается «пропущено», а не «провалено».
Это не отговорка: перед выпуском стоит убедиться, что пропущенных проверок нет.

Отдельно есть самопроверка логики оценки на записанных данных, без обращений к сети:

```powershell
cs2latency.exe --selftest
```

6 сценариев: «до исправления» (пила до роутера), «после» (ровно), ICMP заблокирован,
замер через `ping.exe` без потерь и с потерями 40%, TCP-замер при закрытом ICMP.

## Дефекты, которые нашли тесты

Каждый найден не рассуждением, а падением проверки. Это главная причина, по которой
тесты существуют.

**1. Потоковый баг в GUI.** Модель представления меняла `ObservableCollection`
из продолжения асинхронной проверки, то есть не в потоке интерфейса. WPF отвечает
на это ошибкой «CollectionView не поддерживает изменения из потока, отличного
от Dispatcher», и список находок на реальной машине остался бы пустым.

**2. Запись в реестр не создавала отсутствующий ключ.** `WriteValue` открывал
существующий ключ и при отсутствии молча возвращал `false`. Если настройку удалило
другое приложение, откат не сработал бы — а пользователь считал бы, что программа
вернула всё назад.

**3. Журнал отката был бесполезен при смене версии.** Если обработчик исправления
не найден (переименовали, объединили), запись навсегда застревала в журнале.
Теперь запись откатывается по собственным данным: она хранит ветку реестра, путь
и прежнее значение, а для файла настроек игры — резервную копию.

**4. План исправлений не различал исправление целиком и отдельный параметр.**
Подпункт плана не находился при проверке, и программа молча ничего не делала:
человек нажимал кнопку и не получал ни результата, ни ошибки. Причина была в том,
что по строке идентификатора невозможно понять, исправление это или его параметр —
теперь они хранятся в разных полях, и выбор задаётся явно через `FixTarget`.

**5. Проверка перегрева выдавала ложное предупреждение.** Она брала события журнала
только по коду 37 и находила записи службы точного времени — то есть сообщала
о перегреве процессора там, где его нет. Код 37 пишут несколько источников,
поэтому фильтр обязан идти по источнику события, а не только по коду.
Запрос вынесен в `ThermalCheck.BuildEventQuery` и покрыт тестом: ошибка в фильтре
не падает с исключением — она молча врёт.

**6. Тесты накапливали данные между запусками.** Журнал отката не очищается,
и проверка отката падала на четвёртом прогоне, потому что записей становилось
больше ожидаемого. Идентификаторы в тестах сделаны уникальными для каждого запуска,
а проверяется судьба своих записей, а не общее количество.

## Опасная ошибка в паузе фоновых программ

Самая серьёзная из найденных — и единственная, которую нашли не тесты, а работа
на живой машине.

Первая версия поиска программ по нагрузке ориентировалась на **занятую память**.
Она нашла браузер и среду разработки — они занимают больше всех — и остановила их
вместе с открытыми вкладками и несохранённой работой. Обнаружилось это при
обычной проверке команды `--pause --yes`; программы вернул `--resume`, все запустились.

Принятые меры, каждая закреплена в коде:

| Мера | Где |
|---|---|
| Поиск смотрит только на сетевые соединения, а не на память | `DiscoverBusyApps` |
| Порог поднят с 8 до 12 соединений | там же |
| Список `NeverDiscover` на 90 имён: браузеры, редакторы, компиляторы, менеджеры паролей | `BackgroundAppService` |
| Найденное по нагрузке никогда не отмечается заранее | `MainViewModel` |
| Запрет проверяется и при самой остановке, а не только при составлении списка | `Pause` |
| Тест «Браузеры и редакторы защищены от паузы» на 23 имени | `CoreTests` |

**Вывод на будущее:** функция, которая что-то останавливает или удаляет, не должна
угадывать по косвенным признакам. Нужен явный список того, что трогать нельзя,
и проверка по нему в самой точке действия, а не только там, где строится список.

## Полный цикл проверки на живой машине

Прогон всех ключей на реальном ПК с Windows 10:

```
--fix     : nowindowborder 1 -> 0, бэкап файла создан, журнал записан
--revert  : nowindowborder 0 -> 1, журнал очищен
проверка  : параметры адаптера, USB, планировщик — «уже в порядке»
--history : 3 замера записаны, сравнение выводится
--pause   : опрос нашёл работающие программы, отказ ничего не изменил
--selftest: 6 из 6 сценариев
```

Замер «до/после» подтверждён на этой же машине. После правок сетевой карты
TCP-замер до роутера даёт:

```
до роутера   : 20/20 подключений · медиана 0.9 мс · макс 5.5 мс · отклонение ±1.02 мс
до интернета : 20/20 подключений · медиана 31.4 мс · макс 32.8 мс · отклонение ±0.61 мс
```

До правок тот же участок показывал 19 всплесков из 200 замеров с пиками до 14 мс.
Именно это и есть доказательство результата, а не «стало плавнее».

### Как проверялось окно

Раньше запустить GUI не удавалось, и это было записано в ограничения. Теперь
проверка идёт через дерево интерфейса Windows: окно открывается, кнопки на месте,
диагностика выполняется, списки и блоки заполняются данными.

Что проверяется автоматически:

- окно открывается и видно в системе;
- кнопки «Проверить компьютер», «Применить исправления», «Откатить изменения»,
  «Сохранить отчёт» присутствуют;
- строка версии показывает актуальный номер;
- галочек выбора в списке находок ровно столько, сколько исправимых находок;
- блоки «Сделать руками», «Что изменено», «После исправлений» появляются,
  когда для них есть данные, и скрыты, когда данных нет.

**Чего этот способ не проверяет:** внешний вид. Дерево интерфейса не говорит,
красиво ли выглядит окно и не наезжают ли элементы друг на друга. Для этого нужен
взгляд человека — и один раз это уже дало результат: снимок экрана показал, что
прежние версии выглядели иначе, чем я думал, потому что запускался старый файл.

## Решения, которые стоит знать перед правками

Неочевидные места, где легко сломать то, что работает.

**Связь находок и исправлений.** Идентификатор `FixAction.Id` обязан совпадать
с `IFix.Id`, иначе кнопка не найдёт обработчик. Одно исправление может закрывать
несколько параметров — тогда конкретный указывается в `FixAction.SubActionId`.

**Два похожих случая, которые нельзя путать.** «Проверка нашла проблемы, но исправлять
нечего» и «диагностика не запускалась» выглядят одинаково — пустым планом. Но в первом
случае применять НЕЛЬЗЯ, во втором можно всё. Различает их `FixPlan.BuiltFromFindings`.

**Там, где кнопки быть не может, её и не показываем.** `FixAction.CannotFixNote`
и `CanApplyAutomatically` существуют именно для этого. Раньше VSync и Reflex были
помечены как безопасные, хотя обработчиков для них нет.

**Правило проекта: ни одного молчаливого «не могу».** Это проверяется тестом
«Ни одна проверка не молчит». Если добавляете проверку, которая может не сработать —
обязательно заполняйте `NoHelpReason` и `Recommendation`.

**Замеры не должны врать.** Если узел не ответил вообще — это не «100% потерь»,
а «измерить не удалось». Если `ping.exe` не даёт миллисекунд — их и не показываем,
иначе ноль в отчёте прочтут как «задержка ноль».

**Данные только локально.** Ни `HttpClient`, ни `WebRequest` в проекте нет и быть
не должно. Всё, что программа сохраняет, лежит рядом с ней или в
`%LOCALAPPDATA%\Cs2LatencyDoctor\`.
